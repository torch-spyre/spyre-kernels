# Spyre Kernel Test Skill

Write numerical-equivalence tests for a Spyre-aware kernel against a NumPy/PyTorch
reference, run on **ktir-cpu** via the kernel's committed `.ktir`, including
**distribution invariance** (same result for any core count). Output:
`tests/ktir/test_<name>.py`. For a `_td` kernel (no markers, runs on GPU), use
`td-test`.

## Trigger

Use when asked to write/add tests for a `spyre.py` kernel.

## Pre-flight

1. Run the KB consult in [`../_shared/preflight.md`](../_shared/preflight.md)
   (precision notes for Spyre DL16 can shift tolerances).
2. Read `kernels/vllm/<name>/spyre.py` (signature),
   `kernels/vllm/<name>/lower.py` (the `VARIANTS` that produce
   `<variant>.ktir`), and any existing `tests/ktir/test_<name>.py` (style).
   `kernels/vllm/rms_norm/` is the live example of the full pattern
   (`lower.py` + `tensor_descriptor.ktir` + `tests/ktir/test_rms_norm.py`).
   Confirm the `.ktir` for each variant is committed (regenerated by
   `scripts/gen_ktir.py`).

## Execution path — ktir-cpu is the oracle

A kernel carrying `tl.spyre_tensor_layout` markers **cannot run on stock PyPI
Triton** (the builtin does not exist there), so GPU is not its numerical oracle.
The verification path is:

1. Lower Triton → TTIR → KTIR via the spyre backend (`scripts/gen_ktir.py`, which
   drives `scripts/_spyre/round_trip.py`, does this end-to-end).
2. Execute the KTIR on **ktir-cpu**.
3. Compare against a NumPy/PyTorch reference.

So marked-kernel tests live under `tests/ktir/` (load the committed `.ktir`, run
on ktir-cpu, compare to a NumPy reference) — **not** `tests/triton/` on GPU. The
fixture framework in the spyre Triton tree (`third_party/spyre/test`) is the
canonical reference and includes IR-level assertion helpers (`assert_present`,
`assert_absent`, `assert_result_type`, …) usable from the review side.

> **When GPU is still right.** A `td` (plain-descriptor, unmarked) kernel *does*
> run on stock Triton, so its test is the GPU `@pytest.fixture device` +
> `torch.cuda` pattern comparing against the original kernel — that lives in
> `td-test`. Use the ktir-cpu path here; use GPU there.

Mark CPU-runnable tests with `@pytest.mark.ktir_cpu` (declared in
`pyproject.toml`) so CI can select them. CI collects specific files because some
`tests/ktir/` modules import a kernel's `original.py` at module scope, whose
import-time autotune touches Triton's active driver and crashes on a CPU runner.
Avoid module-scope `original.py` imports, and add each CPU-safe file to the CI
step's list.

## Running the kernel — load the `.ktir`, execute on ktir-cpu

Marked kernels are driven through their **committed `.ktir`**, not `wrapper.py`
on GPU:

```python
from ktir_cpu import KTIRInterpreter

interp = KTIRInterpreter()
interp.load(str(MLIR_PATH))          # kernels/vllm/<name>/<variant>.ktir
outputs = interp.execute_function(
    FUNC,
    input_ptr=x,
    output_ptr=y,
    size=np.int32(size),
    stride=np.int32(stride),
)
result = outputs["output_ptr"]
```

- **Argument names and order must match the committed KTIR signature.** Pass
  buffers and scalars using the emitted names. Pointers come first, followed by
  runtime sizes and strides according to the source signature. Derive strides
  from each array's physical shape so one helper serves every variant (GQA,
  padded head-dim, and folded batch follow from the supplied shapes).
- **Each lowering variant is its own `.ktir`.** Things frozen at lowering — the
  distribution grid (core count), constexpr tile sizes — produce a separate
  `VARIANTS` entry / `<variant>.ktir`. Runtime sizes do **not** need a variant.
- Compile-time constexprs are baked into the `.ktir`; only pointers, runtime
  sizes, and strides are passed at execution time. Document the lowered signature
  in the test module docstring (see `tests/ktir/test_rms_norm.py`).

## Test categories

### 1. Correctness vs a NumPy/PyTorch reference

The oracle is a NumPy/PyTorch reference of the kernel's math (the marked kernel
does not run on GPU, so it cannot be diffed against the original kernel on
device). Parametrize over representative shapes (include non-divisible), use a
fixed seed, random inputs, `numpy`/`torch.testing.assert_close`.

**Tolerances — size to the output dtype's ULP**, via a per-dtype `TOL` dict
(same rationale as `td-test`):

```python
TOL = {
    torch.float32: dict(atol=1e-5, rtol=1e-5),
    torch.float16: dict(atol=1e-3, rtol=1e-3),
    torch.bfloat16: dict(atol=8e-3, rtol=8e-3),
}
```

Loosen *up* only with a stated reason. **Important — matmul / `tl.dot`
reductions:** `tl.dot` and a NumPy `@` reference accumulate the K dimension in
different orders, so a `1e-5` rtol is unrealistic — the project's
`matmul/default` fixture uses **`rtol≈1e-2`**. Align matmul-style tolerances with
that fixture, not the ULP table. **Single-tile cases** (`size <= BLOCK_SIZE`)
have no reduction-order divergence — assert `atol=0, rtol=0`.

### 2. Distribution invariance

The distribution grid is frozen at lowering, so lower a **separate `.ktir` per
core count** (a `VARIANTS` entry each, e.g. `<name>_dist_c{1,4,16,32}.ktir`) and
(a) compare each against the reference and (b) assert results are **bitwise
identical across core counts**. Cover **more cores than work items** (idle cores)
and **single core** (sequential). Size the shape so the work space is more than
one tile (so partitioning actually splits work).

### 3. Lowering assertions (marked kernels)

Read the `.ktir` text and assert the lowering did what the markers intend — cheap
structural checks that catch a silently-wrong lowering the numeric test might miss:

- The expected op is present — `linalg.matmul`, or `linalg.batch_matmul` when a
  batch/head axis should batch (proves heads did not collapse or get mixed).
- **No surviving markers**: no `tt.spyre_tensor_layout` and no `tt.dot` left in
  the KTIR. `RewriteDescriptorLayout` consumes and erases every marker, so
  absence is a valid post-condition (upstream fixtures assert exactly this).
- `scf.for` where a stick loop is expected (a K-reduction over sticks, or a
  parallel multi-stick scatter), and `tensor.insert_slice` where a marked output
  drives the store sink.
- A **dynamic extent** lowered to a `?` (kDynamic) memref dim (`memref<…x?x…>`).

These are assertions about *this repo's* generated KTIR. The pass has no
diagnostic for a consumer it cannot physicalize (`torch-spyre/triton#95`), so a
marked kernel can lower cleanly and still be incorrect. Structural checks plus a
numerical run are required.

`round_trip.py` forwards only `grid`; it does not expose `data_layout` or
`required_fixes`. Marked kernels through this path therefore use
`data_layout="device"` and no fix passes. Upstream numerical layout fixtures use
`data_layout="host"`, which maps a host row-major buffer through the coordinate
map. A variant that requires host interpretation or a fix pass is unsupported by
this generator. See
[`../_shared/spyre/tensor-layout-marker.md`](../_shared/spyre/tensor-layout-marker.md).

### 3b. Inter-tile and layout variants are tested separately

Do not combine `tl.inter_tile` and `tl.spyre_tensor_layout` on the same value.
The marked partial/result becomes physical-rank while the inter-tile identity
remains logical-rank, and lowering fails verification. For a kernel needing both
capabilities, maintain separate variants and test each independently; the
combined path is unsupported.

### 4. Runtime-size (dynamic extent) coverage

When a size is a runtime arg, run **one `.ktir` at several sizes** — include a
size spanning more than one tile (so a runtime-bound reduction loop actually
iterates) and a non-tile-multiple. No re-lowering per size.

### 5. Per-batch / per-head equivalence

When a batch/head axis batches the matmul, assert each slice of the batched output
equals a standalone single-slice reference — proves the `batch_matmul` does not
mix batches.

### 6. Edge cases

Non-divisible shapes; minimum size (< one tile); asymmetric shapes; zero input
(eps); large values; kernel-specific edges (grouped/GQA heads, padded contraction
dim, single batch).

**Stick-multiple caveat.** Every stick-tiled extent must be a multiple of
`S = 128 // dtype_bytes`; a ragged split silently reads out of bounds rather than
failing. So a "non-divisible shape" case must stay non-divisible in the *block*
dimension only — do not sweep a *stickified* extent onto a non-multiple, or the
test encodes broken behavior instead of catching it. Test host-side padding
instead.

## Checklist

1. [ ] Test at `tests/ktir/test_<name>.py`, driven through the committed `.ktir`
       on ktir-cpu (not `tests/triton/` on GPU — the marked kernel can't run there)
2. [ ] Correctness parametrized over shapes vs a NumPy/PyTorch reference
3. [ ] Distribution invariance: a `.ktir` per core count `[1,4,16,32]`; matches
       reference AND bitwise-identical across counts; more-cores-than-work + single-core
4. [ ] Lowering assertions: expected matmul op present, no surviving
       `tt.spyre_tensor_layout`/`tt.dot`, stick loop / insert_slice where expected,
       dynamic extent → `?` memref dim
5. [ ] Runtime-size coverage: one `.ktir` at several sizes (multi-tile + non-multiple)
6. [ ] Per-batch/head equivalence where a batch axis batches the matmul
7. [ ] Edge cases: non-divisible *block* dims, min size, asymmetric, grouped heads,
       padded dim — stickified extents stay stick-multiples
8. [ ] Per-dtype `TOL`; matmul-style `tl.dot` uses fixture rtol (~1e-2), not 1e-5;
       single-tile cases assert `atol=0, rtol=0`; fixed seed everywhere
9. [ ] `@pytest.mark.ktir_cpu` on CPU-runnable tests; no module-scope
       `original.py` import; file added to the CI step's list
